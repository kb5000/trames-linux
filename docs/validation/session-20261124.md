Hardware commands ran as the ordinary guest user through its KVM group.

## Hardware ownership and state checks

Eight hardware tests passed with the automatically selected SMCCC transport,
and all eight passed again with `TRAMES_KVM_TRANSPORT=mmio`:

| Check | Evidence |
| --- | --- |
| Canonical bytes, fork/COW, independent protection, unmap/reuse and invalid/private VA | Actual guest loads/stores and runtime host observations |
| Cached stage-two withdrawal during a host byte borrow | Guest returns its slot with an unready `HardwareWait`; host writes under the gate, release fires readiness, migrated CPU observes the new bytes |
| No-syscall deadline, pre-entry kick and task migration | Sixty slices across two engines retain GPR/PC/NZCV/TLS/all SIMD values; retired handle is inert |
| Host-managed demand-zero HardwareRange | 2 MiB range exports retain canonical bytes, residency metadata and fork/COW isolation |
| Empty sparse table retirement | Unmapping distant VA leaves retires all empty intermediate owners |
| Every EL1 restore PC and both completed-notification branches | Stopped hardware PC selects the full original user checkpoint |
| Actual partial EL1 save | KVM hardware single-step stops inside the save routine; bounded completion returns the pending original SVC with full state |
| Normal continuation cost | 100 warm continuations use 100 SMCCC RUNs or 200 MMIO RUNs; neither resets PC/PSTATE between those calls |

Raw transcripts: [SMCCC](session-20261124/smccc-hardware.txt),
[MMIO](session-20261124/mmio-hardware.txt).
The post-notification restore test covers a bug found during integration:
a kick at the branch after HVC/MMIO must use the full mailbox, rather than
mistaking that PC for a pending save and running past its intended checkpoint.

The original L0 SMCCC/MMIO probes also passed 10,000 round trips during this
batch. Their probe implementation is unaffected by the final VM profile/lease
metadata refactor; its passing result is reused. The new shared-engine tests
above independently cover both transports through task handoff and memory faults.

## Native Linux and complete sessions

The unchanged C fixture was compiled as a native ARM64 static ELF, then compared
with KVM sessions at one and four workers. A second build uses the real dynamic
loader/libc copied into a fresh explicit rootfs. Both transport runs passed all
21 entries: five native references and sixteen KVM cases each.

- Static cases at one/four workers: libc/basic ABI, actual 4 KiB pages,
  mprotect/munmap with two SIGSEGV + siglongjmp recoveries, fork/COW + pipe/wait,
  eight pthreads with separate TLS, futex barrier/join and 40,000 atomic updates,
  and guest exit-code 37 propagation.
- Dynamic rootfs cases at four workers: basic ABI, the same memory/signal checks,
  fork/pipe/wait and the same eight-thread workload.
- Host cancellation interrupts both a pure CPU loop and a sleeping guest at the
  requested 100 ms deadline, using the existing kernel timer/host-wait path.

Raw results: [SMCCC sessions](session-20261124/smccc-sessions.json),
[MMIO sessions](session-20261124/mmio-sessions.json).
Timings are diagnostics on a nested VM, with startup and validation included;
they do not establish bare-metal overhead, transport ranking or a performance
ceiling. Cold asynchronous EL0 capture still reads registers through KVM and
needs measurement/optimization beyond the verified normal mailbox path.

macOS ARM64 strict Clippy and the six ordinary unit/CLI cases passed. Linux
ARM64 strict Clippy and the seven ordinary unit/CLI cases passed; the eight
hardware cases are separately gated/ignored in build-only jobs and were executed
explicitly above. Shared-runtime vendor warnings are unchanged dependencies.
Native Linux release build passed. The earlier standalone L0 musl cross-build
is not claimed for this new session dependency graph, which needs a matching C
cross compiler; native GNU/Linux validation is used here.

## Reproduction and remaining work

Build release on the supported machine, run the hardware commands in README,
and run `scripts/validate-session.py` once per selected transport. The workflow
in `.github/workflows/hardware.yml` requires both transport suites and both
session matrices. The debug VM remains separate from an unattended CI runner.

No GPU/desktop, PCM sound card or video device exists in this VM. Image/FD/sync
contracts, safe external mapping imports and native Vulkan/display/video/audio
providers remain mandatory follow-up work. Full shared mapping/device/resource
pressure, debugger and compatibility corpus acceptance is not implied by these
fixtures. SVE/SME, debugger single-step and exact instruction budgets are not
advertised. The hardware single-step used by one test is a diagnostic facility,
not an implemented guest ptrace single-step ABI.
