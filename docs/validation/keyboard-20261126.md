## Corrected behavior

The host X11 adapter exports the server map through the
[public libxkbcommon-x11 API](https://xkbcommon.org/doc/current/group__x11.html).
It listens to ordered XKB map/state/control events and enables detectable
repeat on its own client. Configuration queries happen at setup or changes;
ordinary keys use physical evdev codes. Native host Wayland forwards the
compositor's XKB-v1 FD, full modifier tuple and repeat-info. A shared map update
creates its retained FD before enqueueing and republishes state to clients
that rebuild their xkb_state. Existing Apple Key callers retain their API.

Original Xwayland applies the received map to its native keyboard and master.
However, [core XTEST injection](https://github.com/mirror/xserver/blob/master/Xext/xtest.c)
always uses a separate XTEST keyboard whose initial US map can replace the
master's map. The existing XWM now enumerates and targets the native keyboard
using XTEST's public XInput event form. Physical keys, full modifier state and
XIM commits share that ordered connection. This also avoids Caps Lock being
toggled twice by concurrent Wayland and XTEST modifier transports. The pinned
XKB Rust binding omits the public modLatches byte; the adapter fills it, and an
original C-header oracle checks the request's size/offsets at **compile time**.

The keyboard gate also exposed a missing native-console poll subscription:
a guest waiting on Wayland plus stdin could sleep until an unrelated GUI event.
The shared byte resource now attaches its retained native console descriptor,
with the correct read/write direction, to the existing execution event queue.
A real socket regression covers wakeup and accepted-resource lifetime. No new
coordinator, resource service thread, polling bus, ordinary-memory barrier or
CPU execution ABI check is introduced. Native desktop errors now retain their
original diagnostic before the shared lifecycle category is reported.

## Reproduction and audit

Install original X11/XKB/Wayland development tools, Xvfb and Weston, including
`libxkbcommon-x11-0`, `libx11-dev`, `x11-xkb-utils` and `x11-xserver-utils`.
The X11 keyboard libraries load only when host X11 desktop mode is selected.
Use the existing desktop rootfs/static Xwayland launcher and the source-checked
guest CLI; no new VM or disk image is required.

```sh
python3 scripts/validate-keyboard.py --unit-binary UNIT --runner TRAMES \
  --receipt BUILD_RECEIPT --rootfs DESKTOP_ROOTFS --launcher LAUNCHER --output NEW_OUT
python3 docs/validation/keyboard-20261126/audit.py --source-root "$PWD"
```

For hosted CI, `--native-only` runs the four native reference/frontend cells on
ARM64 and AMD64 alongside existing native WSI/interop gates. Those jobs make
no KVM or physical GPU claim. Exact cloud statuses and job-log evidence are
recorded in [cloud-checks.json](keyboard-20261126/cloud-checks.json).
