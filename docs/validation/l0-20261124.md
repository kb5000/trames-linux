# First KVM transport validation — 2026-11-24

Result: both real KVM transports passed the implemented L0 probe. Full L0,
shared-runtime sessions, application compatibility and media remain open in the
[implementation ledger](../implementation.md).

- Ubuntu ARM64, Linux `7.0.0-43-generic`, six vCPUs, 8 GiB RAM.
- Actual Linux host page size 4096 bytes; guest stage-1 granule 4096 bytes.
- KVM API 12, user-memory and immediate-exit support, 40-bit maximum ARM IPA,

- Rust `nightly-2026-10-16` / `1.101.0-nightly (4ebd25825 2026-10-15)`.

The hardware probe used the cross-built static ARM64 musl release binary,

## Observed checks

Each transport executed 16 warm-up SVC round trips, then 10,000 measured
round trips. Each measured iteration used one `KVM_RUN`, with no per-register
ioctl in the loop. The handler returns fixture sequence values through the
mailbox; this is transport validation, not a shared Linux getpid implementation.

| Check | SMCCC/HVC | MMIO |
| --- | --- | --- |
| Original SVC → private EL1 → host → ERET | Passed | Passed |
| GPR, SP, NZCV, TLS, FPCR/FPSR and all 32 SIMD registers | Passed | Passed |
| Same RAM bytes observed/modified by host and guest | Passed | Passed |
| Adjacent 4 KiB read-only write fault; neighbor preserved | Passed | Passed |
| PTE/TLBI repair retries original faulting instruction | Passed | Passed |
| Unmapped adjacent page generates fault | Passed | Passed |
| EL0 read of private EL1 mailbox generates fault | Passed | Passed |
| Syscall-free infinite loop interrupted by deadline | Passed | Passed |
| Measured KVM_RUN calls | 10,000 | 10,000 |

Raw reports: [SMCCC](l0-20261124/smccc.json), [MMIO](l0-20261124/mmio.json).
Deadline interrupt elapsed times were about 10.04 ms and 10.24 ms for a 10 ms
one-shot timer. These are observed nested-VM results, not a hard timing bound.

Mean measured time was 32.67 µs (SMCCC) and 33.70 µs (MMIO) per validated round
trip. Timing includes the SVC/EL1/KVM path, full-state checks and mailbox reply,
and excludes warm-up. This is one nested-virtualization sample per transport;
it does not establish a performance ranking, bare-metal exit overhead, or the
product's performance ceiling. Bare-metal host CPU usage, distributions and
application comparisons remain required.

Additional checks passed:

- macOS ARM64: format, strict Clippy, four library and two CLI tests; diagnosis
  reports the unsupported KVM host accurately.
- Linux ARM64 musl: strict Clippy and linked release cross-build, including the
  actual EL1 assembly and KVM backend.
- Linux ARM64 GNU inside the VM: strict Clippy, five library and two CLI tests,
  including a real kernel timer interrupting a blocking thread without KVM.
- Runtime pin/checkout boundary script and hardware script syntax.

Normal CI separately covers Linux amd64, Linux ARM64 and macOS build/unit
checks. The dispatch-only hardware workflow requires a real labelled runner;
the debug VM is not registered as an unattended GitHub runner.

## Reproduction

On the same supported ARM64 Linux configuration, build the release binary and
run `bash scripts/validate-hardware.sh`. Set `TRAMES_BINARY` to use a cross-built
binary and `TRAMES_VALIDATION_OUTPUT` to select the JSON output directory.
Unsupported KVM, pages or explicitly selected transport fail the run.

For the local Mac debug machine, use the bundled Lima with the existing
`target/local-ci/lima` home in the iPad checkout. The instance has
`nestedVirtualization: true`; execute the hardware script through
`limactl shell --workdir /home/main.guest linux -- sg kvm -c '…'`.
An existing SSH session may retain its earlier groups, which is why `sg` was
used after adding KVM access. The writable output share holds the cross-built
binary and JSON; guest builds use a separate `trames-linux-l0` directory.

## Limits and remaining gates

Only one stopped/running owner, one vCPU and a bounded 64 KiB/one-slot RAM arena
are exercised. Concurrent backing borrows/revoke, COW, unmap/reclaim, slot reuse,
pending-exit task migration, asynchronous partial EL1 state recovery and shared
`Cpu`/session dispatch are not implemented by this batch. Baseline state excludes
SVE/SME and exact instruction counting. No ELF/rootfs workload is claimed.

This VM has no `/dev/dri`, desktop display session, PCM sound card or video
device. `/dev/snd` contains only sequencer/timer nodes. It cannot validate real
Vulkan acceleration, presentation, playback/capture or hardware codecs. Those
product gates still require an appropriate Linux GPU/media configuration.
The KVM probe's real 4 KiB mappings do not establish complete runtime/API
4 KiB support; that remains an end-to-end release requirement.
